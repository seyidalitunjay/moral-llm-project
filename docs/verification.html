Method

How equivalence was established

Before a single line was edited, each of the four runnable entry points was executed against the existing data and its output stored. Those stored outputs are the baseline. After the refactor, the same commands were run again and the results diffed against both the baseline and the reports already committed to the repository.

Byte-identical is the standard used throughout, not numerical closeness. The reports are JSON written with a fixed indent, so an identical file means every value agrees to the last digit of its floating-point representation and every key appears in the same order. Preserving key insertion order was a genuine constraint on the rewrite rather than a happy accident, and two places in the code carry comments saying so.

Digests below are the first 16 hex characters of the SHA-256 of each file or captured stream. Three sources are compared where all three exist: the output the refactored code produces now, the report committed in the repository, and the baseline captured from the original code before editing began.

Configuration hash reproduction

A run is addressed by the SHA-256 of its own configuration, which includes the model, sampling parameters, label set, the selected items and every rendered prompt. Reproducing that hash therefore tests far more than the manifest file alone: seeded item selection, prompt construction and parameter defaults all have to agree exactly or the digest diverges. 

$ python3 scripts/run_control_pilot.py --data data/anecdotes.tar \
      --items 20 --samples 10 --max-tokens 4096 --provider parasail

The leading 16 characters name the existing run directory results/pilot_v4/32fa0ec867b00d0c, which holds the 600 responses already collected. The refactored code reaches the same address.

Why the two parsers were not merged

The legacy parser returns the last label appearing anywhere in a response, so it cannot distinguish a stated verdict from one merely discussed. The current parser refuses such responses outright. That difference is a documented finding about the earlier results rather than a bug to be tidied away, so the two live in separate modules, and two tests now assert that they continue to disagree on the cases where the distinction matters.

Pre-existing

Two mismatches that predate the refactor

Two stored artifacts cannot be reproduced by the current code. Both were checked by running the original, pre-refactor scripts, which produce exactly the same mismatch. Neither is caused by the restructuring, and both reflect real revisions made during the project.

pilot_v3 prompts: superseded instruction wording

All 15 prompts stored in the v3 manifest differ from what the current code builds. The anecdote text, the option list and the condition bodies are unchanged; the final-label instruction was rewritten after that run.

- End with exactly one line FINAL_LABEL: <LABEL>, using one allowed label. Do not repeat this marker elsewhere. + On the last line write FINAL_LABEL: followed by exactly one of AUTHOR, OTHER, EVERYBODY, NOBODY. Use the label spelling exactly; no synonyms, Markdown, or punctuation. Do not repeat this marker elsewhere.

The original builder mismatches these same 15 prompts, and the refactored builder agrees with the original on all 90 cases. The v3 run is therefore not regenerable from current code, which is the expected consequence of a prompt revision and is why its responses are kept in their own directory.

v4 smoke run: configuration hash reflects an older parser version

A dry run reproducing the 5-item, 2-sample smoke test yields configuration hash eb1ad6a18e379b31, not the stored 2968f02acc8e2d59. The cause is a single field: the manifest records parser_version: final_marker_cosmetic_v2, while the current parser is exact_label_or_final_marker_v3. The parser version is part of the hashed configuration by design, so revising the parser necessarily re-addresses the run.

Everything else agrees. The same five items are selected, and the manifest produced by the original code is byte-identical to the one produced by the refactored code. The stored run remains fully analysable; reparsing it under the current parser reproduces the committed analysis exactly, as the evidence ledger above shows.

Disclosed changes

Three deliberate differences in behaviour

The refactor was not purely mechanical. Three changes alter behaviour in ways that do not affect any reported figure but are recorded here rather than left for a reader to discover.

Change Effect Bearing on results
The legacy metric script now shares the audit's distribution function Negative or non-finite counts raise ValueError where they were previously accepted and normalised None. Every count in the data is a non-negative integer, and the stdout comparison is byte-identical
compute_metric.py and run_batch.py gained argument parsing Input and output paths are now arguments with defaults. compute_metric.py previously hardcoded results_v2.jsonl in the working directory None to the computation. The invocation changed, and the documented commands were updated to match
run_batch.py checks for the API key at call time rather than import time The module can be imported without a key present, which is what allows it to be inspected and tested offline None. With a key absent the script still exits immediately with an explanatory message

One unused local variable was also removed from the pilot runner. Separately, two hardcoded API keys were replaced with environment variable reads; the affected keys were reported for revocation and the repository has no commit history in which they could persist.

Limits

What this evidence does not cover

The two paid execution paths are unexercised

Running either path costs money at a provider, so neither was executed during verification. In run_control_pilot.py the request loop was extracted from main into its own function, and in run_batch.py module-level code was wrapped in a main. In both cases the statements inside are unchanged and in the same order, but no test covers them.

What was verified around them: the dry run reproduces the configuration hash and manifest exactly; the resume logic reads the correct 60 completed identifiers from the legacy results file; the written record schema matches the existing files key for key; the model, temperature, sample count and pool size constants are unchanged; and the missing-key path exits with the expected message. The resume set, the file lock, the per-record fsync, the consecutive-failure counter and the fatal HTTP status list were reviewed by reading rather than by execution.

Equivalence is not correctness

Everything here establishes that the refactored code computes what the original computed. It says nothing about whether the original was right. The open methodological problems with the study, in particular the uneven parse-failure rate across conditions in the 600-call run, are unaffected by any of this and are recorded separately in the repository's open issues.

Reproduce

Rerunning these checks

None of the following makes a network call or modifies its inputs. The corpus must be present at data/anecdotes.tar; everything else ships with the repository, and the analysis path needs only the standard library. 

python3 scripts/audit_results.py results/legacy/results_v2.jsonl \
    --archive data/anecdotes.tar --out /tmp/audit.json
shasum -a 256 /tmp/audit.json results/reports/audit_report.json

python3 scripts/compute_metric.py

python3 scripts/analyze_control_pilot.py \
    results/pilot_v4/2968f02acc8e2d59 --reparse

python3 scripts/diagnose_responses.py \
    results/pilot_v4/2968f02acc8e2d59/manifest.json \
    results/pilot_v4/2968f02acc8e2d59/responses.jsonl \
    --out /tmp/diagnostics.json

python3 scripts/run_control_pilot.py --data data/anecdotes.tar \
    --items 20 --samples 10 --max-tokens 4096 --provider parasail

python3 -m unittest discover -s tests -v
